# Ch.9 웹 크롤러 설계

## I. 정의
웹에서 새로 올라오거나 갱신된 컨텐츠 찾아내는 것


## II. 대표적 용례

### 검색 엔진 인덱싱
* 웹페이지를 모아 검색 엔진을 위한 로컬 인덱스를 만들기 위해 웹 크롤러 사용(ex. Googlebot)

### 웹 아카이빙
* 나중에 사용할 목적으로 장기보관하기 위해 웹에서 정보를 모으는 과정에서 웹 크롤러 사용
* 대표적으로 국립 도서관이 크롤러를 활용해 웹사이트를 아카이빙하고 있음.

### 웹 마이닝
* 경영 의사 결정 또는 비즈니스 관점에서 유용한 가치를 가진 정보를 수집
* 유명 금융 기업들은 크롤러 활용해 주주총회 또는 기업의 연차 보고서를 확보하여 자금 운용 계획 수립에 활용

### 웹 모니터링
* 저작권 또는 상표권 침해 사례 모니터링 (ex. Digimark)


## III. 설계 (1) : 요구사항 정의 및 개략적 규모 추정

### 기능적 요구사항 정의
* 활용 목적 : 검색 엔진 인덱싱
* 수집 규모 : 웹페이지 10억 개/month
* 새롭게 생성되는 웹페이지 또는 기존에 수집되었거나 수정된 웹페이지도 고려해야함
* 수집된 웹페이지는 5년간 저장
* 중복 컨텐츠 무시 가능

### 비기능적 요구사항 정의
* 규모 확장성 : 웹페이지의 수집 범위가 커져 규모 자체가 커진 상황에도 대응가능하도록 규모 확장성 고려한 설계 필요
* 안정성 : 비정상적 입력 또는 환경에 잘 대응 가능해야 함
* 예절 : 수집 대상 웹페이지를 보유한 웹사이트의 정상적 운용에 지장이 가는 수준의 요청을 보내지 않도록 해야함
* 확장성 : 수집된 웹페이지로부터 추출할 정보가 추가되거나 제거되는 상황을 고려해 설계 해야함.

### 개략적 규모 추정
* QPS = 약 400 Pages / second : 매달 10억 개의 웹페이지 다운로드 하는 경우
* 필요 저장 공간의 크기 = 500TB/month : 웹페이지 평균 500kb 가정.
* 5년 간 보관 위해 필요 저장 공간 크기 = 30PB/5 years


## III. 설계 (2) : 개략적 설계안 및 필요 컴포넌트 정의

* **시작 URL 집합** : 웹 크롤러가 크롤링을 시작할 출발 URL 집합
    * 크롤러가 가능한 많은 링크를 탐색할 수 있도록 하는 URL을 고르는 것이 바람직.
    * 이를 고려해, 전체 URL 공간을 작은 부분 집합으로 나누는 전략 활용
    * ex. URL 공간을 쇼핑, 스포츠, 건강 등의 주제별로 세분화하고, 그 세분화 주제 별로 적절한 시작 URL 을 쓰는 것.
* **미수집 URL 저장소** : 다운로드 할 웹페이지들의 URL 을 저장하는 공간
    * 웹크롤러가 이 저장소로부터 Fetch 하여 작업 수행하는 로직을 고려할 때, FIFO 큐가 적절하여 일반적으로 활용됨
* **HTML 다운로더** : 미수집 URL 저장소로부터 URL을 꺼내 방문하여 해당 웹페이지를 다운로드하는 컴포넌트
* **도메인 이름 변환기(DNS Resolver)** : URL -> IP 변환 컴포넌트
* **컨텐츠 파서** : 다운로드 받은 웹페이지에 대한 파싱 & 검증 수행 컴포넌트
    * 신용할 수 없거나 문제를 일으킬 수 있는 웹페이지 여부를 검증 및 판단
    * 핵심 크롤링 로직에 이를 포함할 경우, 병목이 될 수 있으므로 별도의 컴포넌트로 설계하여 이러한 작업이 비동기적으로 수행될 수 있도록 한다.
* **중복 컨텐츠 검증 컴포넌트 또는 로직**
    * 연구 결과에 따르면, 29% 가량의 웹페이지 컨텐츠가 중복이라고 함.
    * 따라서 이에 대한 검증을 수행하는 컴포넌트를 두어, 이미 방문한 페이지 재방문 또는 중복 저장을 방지하여 성능 및 자원 효율적 설계 가능
* **컨텐츠 저장소**
    * HTML 문서 저장소
    * 저장 데이터의 유형, 크기, 접근 빈도, 유효기간에 대한 고려가 필요.
    * 따라서, 현 설계에서는 메모리와 디스크를 모두 활용하는 저장소 선택.
* **URL 추출기** : HTML 페이지를 파싱하여 링크를 골라냄
* **URL 필터** : 특정 컨텐츠 타입 또는 파일 확장자를 갖는 URL, 접속 시 오류가 발생하는 URL, 접근 제외 목록 등을 크롤링 대상에서 배제하는 역할 수행.
* **이미 방문한 URL 검증 로직 또는 컴포넌트**
    * 미수집 URL 저장소에 존재하는 URL이 이미 방문한 적 있는지 검증하는 컴포넌트.
    * 이를 위한 자료구조로 블룸 필터 또는 해시 테이블을 활용하면 시간복잡도와 공간복잡도 측면에서 효율을 챙길 수 있다.
* **URL 저장소** : 이미 방문한 URL 보관 저장소


## IV. 설계(3) : 세부 설계

### 웹페이지 방문 알고리즘 설계 : DFS or BFS?
* DFS 작동방식 특성 상, 웹페이지 간 참조가 형성하는 유향 그래프의 깊이를 특정할 수 없다는 점에서 한계가 있다.
* 따라서 BFS 를 활용하는 것이 이런 관점에서 유리하다.
* 하지만, 단순히 FIFO Q 하나를 활용해 웹페이지 방문 로직을 설계하는 것은 다음의 문제를 야기할 가능성이 있다.
    1. 한 웹사이트가 보유한 웹페이지는 상호 참조 관계가 일반적 -> 따라서 이를 복수의 멀티 스레드 기반 HTML 다운로더 또는 URL 추출기가 방문할 경우 해당 사이트에 부하를 주는 Impolite 한 크롤링이 될 수 있음.
    2. 목적에 따라 웹페이지 간 우선순위가 다를 수 있음. -> 이를 고려해야함.

### Politeness 와 우선순위 모두 고려하기 위해선? : 똑똑한 미수집 URL 저장소가 필요하다.

기본적인 아이디어는 다음의 두 가지이다.

1. 같은 Hostname 을 가진 URL은 같은 큐에 보관된다.
2. 크롤러의 작업 효율을 고려해, 큐 별로 전담 Worker 스레드를 둔다. 이 워커스레드는 해당 URL을 방문하여 작업을 수행한다.
