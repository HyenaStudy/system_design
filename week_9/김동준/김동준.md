# URL 단축기 설계
- 사실 내용 자체는 어떻게 생성할 것인지가 메인이고 이를 조회해오는 건 단순 데이터베이스 테이블이나 캐시로 읽어오는 내용뿐...

## 1. 62진법 vs 해시

| 구분           | Base62 (ID 기반)        | Hash 기반               |
| ------------ | --------------------- | --------------------- |
| 기본 아이디어      | 고유 ID를 62진법으로 변환      | 원본 URL을 해시해서 코드 생성    |
| 입력           | DB ID (정수)            | 긴 원본 URL              |
| 출력           | Base62 문자열            | 해시 문자열 일부             |
| 가역성          | 가역적 (Base62 ↔ ID) | 비가역적              |
| 충돌 가능성       | 없음                  |  있음                  |
| 충돌 처리        | 불필요                   | 필수 (재시도 / 길이 증가)      |
| 코드 생성 방식     | 순차적                   | 결정적 또는 랜덤             |
| 순서 노출        | 있음                  | 없음                  |
| 예측 가능성       | 높음                  | 낮음                  |
| 구현 난이도       | 낮음                    | 중간                    |
| 성능           | 매우 빠름                 | 빠르나 해시 계산 필요          |
| URL 중복 처리    | 별도 로직 필요              | 자연스럽게 처리 가능           |

- 처음 봤을 떄, 62진법 기반 전환이 해시함수의 일종이 아닌가... 싶었지만, 해시의 전제는 **비가역성**임
- 62진법 전환은 역으로 10진법 전환이 가능한, 가역적 연산이므로 해시 연산이 아니다

## 2. 문득 든 생각, 두 방법을 같이 쓰면 경우의 수가 더 늘어나지 않나?
- 두 방법을 순열처럼 순서만 달리하고 동시에 적용하면 더 단축된 URL을 추출할 수 있지 않나...
- 라고 생각해서 GPT한테 물었는데 너 정말 핵심을 찔렀다면서 틀렸다고 함....
### (1) 가역성과 비가역성의 문제
- 위에 적었듯, 진법전환은 가역적이고 해싱은 비가역성이 전제됨
- 진법전환은 결국 표현의 차이(Encoding)이고, 해싱은 출력값만으로는 원본을 찾지 못함(Hashing)
- 함수 관점에서 진법전환은 역함수가 존재하는 일대일 대응이지만, 해싱은 역함수가 존재하지 못함
- 결국 순서를 달리해서 가역함수와 비가역함수를 섞더라도, 수학적으로 가역함수와 비가역함수의 합성함수는 무조건 비가역함수가 도출됨
### (2) 그래서 URL 생성과 무슨 관계?
- URL 단축은 **리다이렉팅**이라는 전제 조건이 있음. 달리 말하면 **가역성**을 요구하거나 **해싱 입출력의 레코딩**이 요구됨
- 결국, 한번 해싱할 거를 괜히 중간에 복잡한 연산 하나 더 추가된 또다른 해싱에 불과할 뿐
- 경우의 다양성은 늘어나지 않고 테이블 레코딩 한계는 그대로임
