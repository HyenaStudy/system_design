## 웹 크롤러 설계

**웹 크롤러?**

- 웹 페이지를 자동으로 다운로드 → 페이지 안의 url 추출 → 새로운 페이지를 수집하는 시스템

**주요 활용 사례**

- 검색 엔진 인덱싱
- 웹 아카이빙 (장기 보관)
- 웹 마이닝 (데이터 분석)
- 웹 모니터링 (저작권 침해, 브랜드 감시 등)

**인터뷰에서 반드시 먼저 확인해야 할 질문**

- 크롤러의 목적은 무엇인가? (검색 / 아카이빙 / 분석)
- 수집해야 할 페이지 규모는?
- 신규 페이지 / 수정된 페이지도 고려해야 하는가?
- 중복 콘텐츠는 어떻게 처리할 것인가?
- 수집한 데이터는 얼마나 오래 저장해야 하는가?

**예시 요구사항 (책의 가정)**

- 매달 약 10억 개 웹 페이지 수집
- 5년간 저장
- 평균 페이지 크기 500KB
- 대략 월 500TB, 5년이면 약 30PB 저장 필요
- Peak QPS 약 800

### 2. 웹 크롤러의 핵심 속성

**확장성**

- 웹은 사실상 무한에 가까움
- 병렬 처리 없이는 불가능
- 수평 확장 가능한 구조 필요

**안정성**

- 깨진 HTML
- 응답 없는 서버
- 악성 링크
- 비정상적인 리다이렉트 등
- 크롤러는 망가진 입력에 강해야 함

**예의**

- 동일 서버에 짧은 시간에 과도한 요청 금지
- 무례한 크롤러는 DoS 공격으로 간주될 수 있음
- 서버별 요청 속도 제한 필요

**확장성**

- HTML만 수집하다가
- 이미지, PDF, 비디오 등으로 확장 가능해야 함
- 새 콘텐츠 타입 추가 시 전체 시스템 재설계는 피해야 함

### 3. 전체 아키텍처 개요

**기본 구성 요소**

- 시작 URL 집합
- 미수집 URL 저장소
- HTML 다운로드기
- 도메인 이름 변환기
- 콘텐츠 파서
- 중복 콘텐츠 판별기
- URL 추출기
- URL 필터
- 이미 방문한 URL 저장소
- 콘텐츠 저장소

**전체 흐름 요약**

- 시작 URL → 미수집 URL 저장소
- URL을 하나 꺼내 다운로드
- HTML 파싱 및 검증
- 중복 콘텐츠인지 확인
- 신규 콘텐츠 저장
- 링크 추출
- 필터링
- 이미 방문한 URL 제거
- 다시 미수집 URL 저장소로 추가

### 4. URL Frontier 설계 (미수집 URL 저장소)

**역할**

- 아직 방문하지 않은 URL 관리
- 크롤링 순서 결정의 핵심

**기본 자료구조**

- FIFO 큐 (BFS 기반)
- DFS는 깊이 편향 문제로 부적합
- BFS는 넓게 퍼지며 공정하게 수집

**이미 방문한 URL 추적**

- 동일 URL 재수집 방지
- 무한 루프 방지
- 서버 부하 감소

**사용되는 자료구조**

- 해시 테이블
- 블룸 필터
    - 메모리 효율적
    - 거짓 양성 가능
    - 없다 판단에 매우 효과적

### 5. HTML 다운로드

**역할**

- HTTP 프로토콜로 웹 페이지 다운로드

**고려 사항**

- Robots.txt 준수
- 타임아웃 설정
- 예외 처리 필수

**Robots.txt**

- 크롤러 접근 허용/차단 규칙 정의
- User-agent 별로 규칙 다를 수 있음
- 주기적으로 캐시해서 재사용

### 6. 중복 콘텐츠 처리

**문제**

- 연구 결과 약 29% 웹 페이지는 중복 콘텐츠
- 동일 내용이 URL만 다른 경우 매우 많음

**단순 비교의 한계**

- HTML 문자열 직접 비교 → 비효율적
- 10억 문서 비교는 불가능

**해결 방법**

- 페이지 해시값 비교
- 이미 저장된 해시가 있으면 중복으로 판단
- 중복 페이지는 저장 생략

### 7. URL 추출 및 필터링

**URL 추출**

- HTML 파싱 후 a 태그 등에서 링크 수집
- 상대 경로 → 절대 경로로 변환

**URL 필터**

- 특정 파일 타입 제외
- 에러 URL 제외
- deny list 기반 필터링

### 8. 예의 있는 크롤링

**문제 상황**

- 한 페이지에서 나온 링크 대부분이 동일 호스트
- 병렬 처리 시 특정 서버에 요청 폭주

**해결 전략**

- 호스트별 큐 분리
- 동일 호스트는 같은 큐로
- 큐 라우터 + 큐 선택기 구조

**구성**

- 큐 라우터
    - URL을 호스트 기준으로 큐에 배치
- 큐 선택기
    - 여러 큐를 순회하며 URL 선택
- 워커 스레드
    - 실제 다운로드 수행
    - 요청 간 delay 유지

### 9. 우선순위 기반 크롤링

**왜 필요한가**

- 모든 페이지가 동일한 가치가 아님
- 중요 페이지 먼저 수집해야 함

**우선순위 기준 예시**

- 페이지 랭크
- 트래픽
- 업데이트 빈도
- 도메인 신뢰도

**구조**

- 순위 결정 장치 (prioritizer)
- 우선순위별 큐
- 높은 우선순위 큐에서 더 자주 선택

**프론트 큐 / 백 큐 분리**

- 프론트 큐: 우선순위 계산
- 백 큐: 예의 보장 (호스트별 제한)

### 10. 신선도 (Freshness)

**문제**

- 웹 페이지는 계속 변경됨
- 한 번 수집으로 끝나지 않음

**전략**

- 변경 이력 활용
- 중요한 페이지는 더 자주 재수집
- 덜 중요한 페이지는 주기 늘림

### 11. 성능 최적화

**분산 크롤링**

- 여러 서버에서 병렬 수행
- URL 공간을 분할해 담당

**DNS 캐싱**

- DNS 조회는 동기 + 느림
- 결과 캐시 필수
- 주기적 갱신

**지역성 활용**

- 크롤링 서버를 대상 서버와 물리적으로 가깝게 배치
- 다운로드 지연 감소

**짧은 타임아웃**

- 느린 서버 기다리지 않음
- 빠르게 다음 작업으로 이동

### 12. 안정성 고려

**지속성 저장**

- 크롤링 상태 저장
- 장애 발생 후 재시작 가능

**예외 처리**

- 개별 에러가 전체 시스템 중단으로 이어지지 않도록
- 실패한 URL은 로그 후 재시도 또는 폐기

**데이터 검증**

- 잘못된 데이터 유입 방지

### 대규모 크롤러에서의 분산 스케줄링

- 중앙 URL Frontier 병목 문제
- 샤딩된 Frontier 구조

## 알림 시스템 설계

### 1. 문제 이해 및 설계 범위 확정

**알림 시스템이란**

- 사용자에게 중요한 정보를 **비동기적으로 전달**하는 시스템
- 뉴스, 이벤트, 결제, 배송, 마케팅 등 대부분의 서비스 핵심 기능

**지원해야 할 알림 유형**

- 모바일 푸시 알림
- SMS 메시지
- 이메일

**실시간성 요구**

- 연성 실시간(soft real-time)
- 가능한 빠르게 전달하되, 과부하 시 약간의 지연 허용

**지원 단말**

- iOS
- Android
- SMS 수신 단말
- 이메일 수신 단말(웹/데스크톱)

**알림 생성 주체**

- 클라이언트 앱
- 서버 (배치, cron, 이벤트 기반)

**기본 요구사항 정리**

- 하루 수천만~수억 건 알림 처리
- 사용자 opt-out(수신 거부) 지원
- 알림 중복 최소화
- 장애 발생 시 알림 유실 방지

### 2. 알림 유형별 지원 방식

**iOS 푸시 알림**

- APNS(Apple Push Notification Service) 사용
- 알림 제공자 → APNS → iOS 단말
- 필요 데이터
    - device token
    - payload(JSON)
- APNS는 실제 전송만 담당, 로직은 서버 책임

**안드로이드 푸시 알림**

- FCM(Firebase Cloud Messaging) 사용
- APNS와 구조 거의 동일
- 플랫폼별 전송 서비스만 다름

**SMS**

- 보통 제3자 서비스 사용
- 비용 발생, 신뢰성 높음

**이메일**

- 자체 메일 서버 또는 외부 서비스 사용
- 분석, 성공률, 트래킹 기능 제공

### 4. 알림 전송 및 수신 절차

**전체 흐름**

1. 서비스가 알림 서버 API 호출
2. 알림 서버가 사용자/단말/설정 정보 조회
3. 알림 이벤트 생성
4. 알림 유형별 메시지 큐에 적재
5. 작업 서버(worker)가 큐에서 메시지 소비
6. 제3자 서비스로 전송
7. 사용자 단말 수신

### 5. 개선된 알림 시스템 아키텍처

**핵심 개선 포인트**

- 메시지 큐 도입
- 알림 서버와 전송 로직 분리
- 알림 유형별 큐 분리

**구성 요소**

- 알림 서버
    - 인증
    - 전송 제한
    - 메타데이터 조회
- 캐시
    - 사용자 정보
    - 단말 정보
    - 알림 템플릿
- 데이터베이스
    - 사용자
    - 설정
    - 알림 로그
- 메시지 큐
    - iOS 큐
    - Android 큐
    - SMS 큐
    - Email 큐
- 작업 서버
    - 큐 소비
    - 실제 전송 수행

### 6. 안정성 (Reliability)

**데이터 손실 방지**

- 알림 이벤트를 DB에 로그로 저장
- 장애 발생 시 재처리 가능

**재시도 메커니즘**

- 전송 실패 시 재시도 전용 큐로 이동
- 지정 횟수 초과 시 alert 발생

**SPOF 제거**

- 알림 서버 다중화
- 작업 서버 수평 확장 가능

### 7. 알림 중복 전송 방지

**문제**

- 분산 시스템 특성상 정확히 한 번(exactly-once) 전송은 불가능

**현실적인 접근**

- 이벤트 ID 기반 중복 감지
- 이미 처리한 이벤트는 무시

**중복 방지 로직**

- 이벤트 도착 시
    - event_id 확인
    - 이미 처리된 이벤트면 discard
    - 아니면 전송

### 8. 알림 템플릿

**왜 필요한가**

- 알림 메시지 대부분 구조가 유사
- 매번 직접 생성하면 오류 증가

**템플릿 역할**

- 메시지 포맷 통일
- 파라미터만 주입
- 작성 시간 단축
- 일관성 유지

**예시**

- 제목 + 본문 + CTA
- item_name, date 등 변수 치환

### 9. 알림 설정 (User Preference)

**문제**

- 너무 많은 알림 → 사용자 피로
- 알림 기능 자체를 꺼버릴 위험

**설정 정보**

- user_id
- channel (push, email, sms)
- opt_in 여부

**전송 전 필수 체크**

- 해당 알림 유형 수신 허용 여부

### 10. 전송 제한 (Rate Limiting)

**목적**

- 사용자 알림 폭주 방지
- 서비스 신뢰도 유지

**방식**

- 사용자별 알림 빈도 제한
- 시간당/일별 전송 횟수 제한

### 11. 보안

**API 보호**

- appKey / appSecret 기반 인증
- 승인된 클라이언트만 알림 전송 가능

**이유**

- 스팸 알림 방지
- 외부 공격 차단

### 12. 큐 모니터링

**중요 메트릭**

- 큐에 쌓인 메시지 수
- 처리 지연 시간

**의미**

- 큐 backlog 증가 → 작업 서버 부족
- worker scale-out 필요 신호

### 13. 이벤트 추적 (Analytics)

**추적 이벤트**

- 알림 전송 성공/실패
- 사용자 수신
- 클릭
- 수신 거부

**목적**

- 알림 효과 분석
- UX 개선
- 비즈니스 의사결정 지원

### 14. 최종 설계 요약

**개선된 설계에서 추가된 요소**

- 인증(authentication)
- 전송 제한(rate limiting)
- 재시도 큐
- 템플릿 시스템
- 알림 로그 저장
- 모니터링 및 이벤트 추적

**핵심 설계 철학**

- 비동기 처리
- 컴포넌트 간 결합도 최소화
- 실패를 전제로 한 설계
- 확장성과 안정성 우선
