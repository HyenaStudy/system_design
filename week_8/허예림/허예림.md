## URL 단축기 설계

### 1. 문제 이해 및 범위 확정

- 목표
    - 입력: 긴 URL
    - 출력: 짧은 URL(도메인/짧은키)
    - 짧은 URL 접속 시 원래 URL로 리디렉션
- 트래픽 및 제약
    - 매일 1억개의 단축 URL 생성
    - 읽기:쓰기 비율은 10:1 가정
    - 단축 키에 사용할 수 있는 문자는 0-9, a-z, A-Z(62개)
    - 삭제/갱신 없음 가정
    - 짧을수록 좋음

### 2. API 엔드포인트

- 단축 생성
    - POST /api/v1/data/shorten
    - 요청: { longUrl: longURLString }
    - 응답: shortUrl
- 리디렉션
    - GET /api/v1/shortUrl
    - 응답: 301 또는 302 + Location 헤더에 원래 URL

### 3. 개략적 추정

- 10년 보관(가정)
    - 1억 × 365 × 10 = 3650억 레코드
    - 원본 URL 평균 길이 100바이트 가정
    - 필요 저장용량 3650억 × 100B
    - (실제로는 인덱스/메타데이터/오버헤드로 더 증가)

### 4. 핵심 플로우

- 단축 생성 흐름(공통)
    - 입력 longURL
    - 이미 같은 longURL이 존재하는지 확인
    - 있으면 기존 shortURL 반환
    - 없으면 새 shortURL 생성 후 (shortURL, longURL) 저장
    - shortURL 반환
- 리디렉션 흐름(공통)
    - shortURL로 요청
    - shortURL → longURL 매핑 조회
    - 301/302로 Location: longURL 반환

## 단축 키 생성 전략

### 1. 해시 기반 + 충돌 해소

- 개념
    - longURL을 해시 함수로 변환 → 해시값 일부를 잘라 shortKey로 사용
    - DB에 (shortKey, longURL) 저장
- 장점
    - shortKey 길이를 고정하기 쉬움
    - 별도의 전역 ID 생성기가 없어도 시작 가능
- 단점/리스크
    - 해시를 일부만 쓰면 충돌 가능성이 증가
    - 충돌 시 재시도(예: longURL 뒤에 사전 정의 문자열을 붙여 다시 해시) 필요
    - 충돌 여부 확인을 위해 DB 조회가 추가로 들어갈 수 있음(오버헤드)
    - 충돌 확인 시 DB 조회 오버헤드를 줄이기 위해 블룸 필터 사용 가능

### 2. Base62 변환

- 전역 유일 ID를 발급
- ID를 base62로 변환해 shortKey 생성
- DB에 (id, shortKey, longURL) 저장
- shortKey 길이 산정
    - 사용 가능한 문자 수 : 62
    - 10년 보관량이 3650억 레코드라면, 62^n ≥ 3650억을 만족하는 n이 필요
    - n=7이면 62^7 →  3500 (충분) → 길이 7 선택
- 장점
    - 충돌이 원천적으로 없음(전역 유일 ID가 전제)
    - 생성 시 충돌 해소 루프가 없어 단순
- 단점/리스크
    - ID 생성기가 필요
    - 시간이 지나 ID가 커질수록 shortKey가 길어질 수 있음
    - 단순 증가 ID면 추측 가능(보안/크롤링/남용 리스크)

## 데이터 모델

### 1. 테이블

- url
    - id (PK)
    - shortURL
    - longURL
- 인덱스 관점
    - shortURL 유니크 인덱스
    - longURL 인덱스

### 캐시

- 읽기가 훨씬 많으므로 shortURL → longURL 매핑을 캐시에 올려둔다
- 캐시 hit면 DB 없이 바로 리디렉션 응답
- 캐시-어사이드
    - 요청 → 캐시 조회
    - hit: longURL 반환
    - miss: DB 조회 → 캐시에 적재 → longURL 반환
