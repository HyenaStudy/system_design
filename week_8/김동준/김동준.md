# 분산 시스템을 위한 유일 ID 설계
## 1. 전제조건
1. 유일하며, 정렬 가능하다
2. 시간에 따라 증가하는 단조성을 보인다
3. 노드는 ID 생성 정책을 몰라도 정렬이 가능하다
4. 생성 책임을 지는 중앙집중 컴포넌트는 최대한 배제한다
## 2. 나름대로 떠올린 분산 ID 생성 로직
### (1) 힐베르트 호텔
- 가장 먼저 떠오른 건 [힐베르트 호텔](https://ko.wikipedia.org/wiki/%ED%9E%90%EB%B2%A0%EB%A5%B4%ED%8A%B8_%ED%98%B8%ED%85%94)
- 요약하자면 **셀 수 있는 무한에 대한 사고실험**
- 유일성과 단조성을 만족한 채로, 새로운 재배치가 있어도 중복을 허용하지 않는다
- 하지만 재배치의 책임이 호텔 카운터(중앙집중)에 몰려서 4번 불만족, 단일장애점 이슈
### (2) 소수 곱 해싱
- 분산 노드별로 소수를 부여하고, 요청의 타임스탬프에서 소수를 곱한다
- 이러면 1번과 4번 요구사항을 무조건 충족 가능하다
- 하지만 2번과 3번을 만족하지 못한다
- 2번을 위해서 역해싱이 필요한데, 이 말은 해싱 정책을 노드가 기억하고 있어야 한다
### (3) 내 생각들이 부딪힌 한계의 공통점
- ID 생성의 기준축은 2개다. **시간**과 **노드들**
- 시간은 절대적이고 단조적이기 때문에 정책의 기억과 설명 없이도 직관적인 이해가 가능하다(절대부등식)
- 하지만 노드들은 병렬적이기 때문에 노드는 순서 계산의 보조축에 불과하지, 순서 자체를 생성할 수는 없다
- 그래서 소수 곱 해싱이 우선 안되는 것이고(노드들이 순서 요소에 적극 개입하므로) 힐베르트 호텔은 이를 극복하려 했으나 중앙집중화를 막지 못했다
- 결론은 시간 축보다 노드 축이 더 앞선, 실패 사례라고 볼 수 있겠다
## 3. 왜 트위터의 스노우플레이크가 적절한 ID일지
### (1) 개념
- 사실 절대적 단조성을 만족하는 요소는 결국 시간이고 스노우플레이크는 시간을 자릿수처럼 활용함
<img width="80%" alt="image" src="https://github.com/user-attachments/assets/b2542f2b-b456-47a3-bfcb-75864555a6ad" />
- `timestamp` : 시스템 전역에 대한 순서 식별
- `instance` + `sequence` : 동일 타임스탬프 내에서 노드 내에서의 순서 식별
- 이를 통해 분산 시스템에서의 고유성 및 중앙집중화를 배제하는 소기의 목표를 달성한다
### (2) 다른 것들과의 비교
- **UUID** : 1번과 2번 위배
- **티켓 서버(중앙 시퀸스)** : 4번 위배
- **다중 마스터** : 충돌을 전제하고 발생시, 사전에 기억시킨 정책으로 노드에서 알아서 해석하므로 3번 위배
