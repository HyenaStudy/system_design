# 분산 시스템을 위한 유일 ID 생성기 설계

분산 시스템이라고 다를 것이 있을까, 그냥 DBMS 하나를 단일 ID 공급원으로 활용하면 되지 않을까, 생각할 수 있다.

하지만 크게 두 가지 한계로 인해 위의 방안은 실효성 측면에서 문제가 있다.

1. 단일 DBMS 의 처리량 한계
 - MySQL 의 대표적 Storage Engine 인 InnoDB 는, `auto-increment` 방식의 ID 생성 시, 동시성 제어를 위해 Gap-lock 을 활용한다. 물론, 오랜 기간 동안 대규모 트래픽 상황에서의 성능은 검증이 된 DBMS & 엔진이지만, Lock 으로 인해 구조적 한계가 명확하다.
2. 여러 데이터베이스를 활용하는 경우, 이들 간 동기화로 인한 필연적 지연시간
 - 유일 ID 발급이라는 목표를 달성하기 위해선 복수의 DB 간 '서로 어떤 ID 까지 발급했는가' 에 관한 최신화된 정보를 공유할 필요가 있다. 그렇기 때문에, 트래픽 규모가 큰 상황에서는 이러한 동기화에 필요한 지연시간으로 인해, ID 생성이 전체 시스템 처리량의 발목을 붙잡는 요소가 될 가능성이 충분하다.

따라서, 우리는 좀 더 영리한 방법을 찾아보기로 한다.

## I. 문제 이해 및 설계 범위 확장

이 책에서는 지원자와 면접자 간 질의응답을 통해 모호한 요구사항을 뾰족하게 다듬어 간다.

이러한 대화 과정은 잠시 생략하고, 결과적으로 도출된 요구사항을 정리하기로 한다.

> [!NOTE]
> **분산 시스템을 위한 유일 ID 생성기 설계 : 확정 요구 사항**
> - ID는 유일할 것
> - ID는 숫자로만 구성될 것.
> - ID 는 64비트로 표현할 수 있는 값일 것.
> - ID는 발급 시점 기준 시계열 정렬이 가능할 것.
> - 초당 10,000 개의 ID를 생성할 수 있을 것.

## II. 개략적 설계안 도출
책에서는, 앞서 정의한 세부 요구사항을 만족하는 유일 ID 생성을 위해 크게 네 가지의 설계 방안을 가안으로 제시하고, 하나씩 타당성을 검증한다.

### 다중 마스터 복제
<img width="401" height="201" alt="Screenshot 2026-01-17 at 4 11 01 PM" src="https://github.com/user-attachments/assets/5505070e-d9ea-48d1-9fc2-e1ca3bde40ea" />

**작동방식**
 - DB의 auto_increment 기능을 활용.
 - 이때, 단일 DB 활용 때와 다르게, 1이 아닌, `k` 만큼 증가된 ID를 생성하는 방식

**장점**
 - 규모 확장성 문제를 어느 정도 해결할 수 있다. : 단일 DB 대비
 - DB 수 확장 시, 초당 생상 ID 수도 늘릴 수 있음.

**단점**
 - 여러 데이터 센터에 걸쳐 규모를 확장하기 어려움.
 - ID 유일성은 보장 가능하나, '시간 흐름에 맞추어 ID가 커지도록 보장할 수 없음'
   - ex. DB A, B가 있고 이때, Routing 매커니즘 상의 특성으로 인해 A가 생성한 ID가 지난 3초 간의 ID 발급 요청에 대해 발급되었다고 가정하자(1, 3, 5).
   - 그렇다면 이후에 B 가 생성한 ID 는 발급 시간 상 앞선 세 요청 보다 늦음에도, 더 적은 ID 발급 받게됨.
 -  서버를 추가하거나 삭제할 때에도 잘 동작하도록 만들기 어렵다. : 서버를 Consumer 로 바라볼 때, 서버의 확장 및 축소는 Consumer 측의 ID 소비 속도와 직결된다. 이에 유동적으로 대응하여 일관성 있는 ID 발급에 한계가 있다는 것.
  
### UUID(Universally Unique Identifier)

**작동방식**
- 버전에 따라 조금씩 다르지만, 일반적으로 널리 활용되는 UUID v4 는 무작위에 가까운 난수에 근거하여 ID를 생성하고 UUIDv7은 시간 데이터를 활용한다.
- 길이는 128비트이다.
- 각 웹 서버마다 UUID 생성기를 독립적으로 활용하여, 동기화에 관한 고려 없이 독립적으로 ID를 생성 및 발급하는 구조가 된다.

**장점**
 - UUID 를 만드는 것은 단순하고, 서버 사이의 조율이 필요 없는 독립적 생성 발급이 가능하므로 동기화 이슈도 없다.
 - 규모 확장이 용이함
**단점**
 - ID 길이가 128비트 -> 다소 길다. 또한, 이번 문제의 요구사항은 64비트이므로 적합하지 않음.
 - 시간순 정렬 불가 : UUID v7은 가능하다. 또한 이러한 점을 인지하고 나온 TSID 와 같은 대안도 존재.
 - ID에 non-numeric 데이터가 포함될 수 있음.

### 티켓 서버
<img width="499" height="193" alt="Screenshot 2026-01-17 at 4 34 17 PM" src="https://github.com/user-attachments/assets/35161524-51d9-40c8-b73d-3b15f96da222" />

플리커(Flikr) 가 분산 기본키(Distributed Primary Key) 생성 방안으로 선택한 이 전략을 살펴보자!

**작동방식**
 - `auto_increment` 기능을 갖춘 DB 서버를 ID 생성 & 발급하는 '티켓 서버'로 활용하는 중앙 집중형 시스템 설계.

**장점**
 - 유일성이 보장되는 '오직 숫자로만 구성된 ID'를 쉽게 생성 및 발급 가능.
 - 구현이 용이하고 중소 규모 애플리케이션에 적합.

**단점**
 - 티켓 서버가 SPOF 가 된다.
 - 이를 극복하기 위해선 티켓 서버 다중화가 필요한데, 이 경우 역시 '동기화로 인한 지연시간 이슈'가 대두된다.

### 트위터 스노우플레이크 방식의 접근
<img width="500" height="71" alt="Screenshot 2026-01-17 at 4 48 58 PM" src="https://github.com/user-attachments/assets/213c7357-d320-4b9b-b558-f9240199ff47" />

_Divide & Conquer_ 전략으로 ID를 생성하는 방식이다.

각 세그먼트별로 할당된 비트의 수, 즉 '세그먼트의 길이'만큼 더 많은 경우의 수가 가능하다는 점을 주목해야한다.

이러한 관점으로 이 방식을 다시 살펴보면, 이 ID 생성 전략에서 '고유성'에 대한 책임을 각각 다른 가중치로 개개의 세그먼트에게 부여하고 있음을 알 수 있다.

**작동방식**
 - Sign 비트 : 당장은 필요하지 않을 수 있지만, 추후 활용 가능성을 고려해 할당.
 - 타임스탬프 : 41비트 길이. 기원시각(Epoch) 이후로 경과한 Millisecond 를 비트로 표현한 세그먼트.
 - 데이터센터 ID : 5비트 할당. 총 32개의 데이터 센터 지원 가능.
 - 서버 ID : 5비트 할당. 데이터 센터 ID와 조합할 경우, 총 1,024개의 서버*데이터센터 쌍이 실현 가능함을 알 수 있다.
 - 일련번호 : 12비트 할당. **1 밀리초 마다 0으로 초기화.** -> 동시 요청의 경합도를 고려했을 때, '짧은 시간 내에 많은 발급 요청이 발생할 때, 한정된 범위의 수로, 최대한 많은 고유 ID를 발급하기 위한' 메커니즘이다.

**결론적으로 이 방식은 ID 생성에 관한 아래의 요구사항을 모두 만족한다.**
> - ID는 유일할 것
> - ID는 숫자로만 구성될 것.
> - ID 는 64비트로 표현할 수 있는 값일 것.
> - ID는 발급 시점 기준 시계열 정렬이 가능할 것.

처리량에 관한 요구사항은 설계에 따라 다를 수 있지만 충분히 가능하다는 점에서, 가장 선택 가치가 높은 방안이다.

## III. 상세 설계

### 타임스탬프
<img width="505" height="394" alt="Screenshot 2026-01-17 at 4 57 57 PM" src="https://github.com/user-attachments/assets/5804f2ba-4858-40f3-b7f3-0e301152375d" />

 - 이 세그먼트는 41비트의 길이를 가지며, 기원시각 기준 경과한 Milliseconds 를 비트로 표현한 것.
  - 따라서 시간이 지남에 따라 값이 증가함 -> 시계열 정렬 가능.
 - 단순한 계산을 통해 UTC 시각 <-> 41 비트 길이의 이진 숫자 간 변환이 용이함.
 - 하지만 현행 설계 상, 총 69년 동안 유일 ID를 생성 및 발급 가능. -> 이후엔 기원 시각을 바꾸거나 ID 체계를 변경하는 방안이 필요.

### 일련번호
 - 높은 동시성이 요구되는 상황에서, 한정된 비트 길이를 활용해 최대한 많은 고유 ID를 생성할 수 있도록 1 ms 마다 초기화되는 세그먼트.

## IV. 마무리 - 남은 질문들
### 시계 동기화
 - 현 문서에서는 편의 상 분산 시스템 상 모든 서버의 시각이 정확하게 동기화되는 것으로 가정했으나, 실제로는 그렇지 않음.
 - 그렇기 때문에 이와 같인 '분산 시스템 상의 Physical Time 차이를 최대한 정밀하게 조율하기 위해 활용되는' NTP 를 살펴보면 좋다.

### 각 세그먼트 길이 최적화
 - 필요에 따라, 각 세그먼트에 할당된 길이를 조정하는 방향으로, 필요에 맞도록 최적화가 가능.
   - ex. 낮은 동시 발급 요구가 자명되는 경우 -> 일련번호 세그먼트 길이를 줄이고, 타임스탬프 세그먼트의 길이를 늘려 '더 오래 활용할 수 있는 ID 생성 방안'을 설계할 수 있음.
