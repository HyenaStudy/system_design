# ch 9. 웹 크롤러 설계

## 1. 문제 이해 및 설계 범위 확정

### 웹 크롤러의 기본 동작

웹 크롤러는 다음 과정을 반복한다.

1. 시작 URL 집합을 입력으로 받아 웹 페이지를 다운로드한다.
2. 다운로드한 웹 페이지에서 새로운 URL을 추출한다.
3. 추출된 URL을 다시 수집 대상에 추가하고 위 과정을 반복한다.

이 과정은 웹 전체를 하나의 **유향 그래프**로 보고,  
노드(페이지)와 에지(링크)를 따라 탐색하는 문제로 볼 수 있다.

## 2. 개략적 설계안

**(1) 시작 URL 집합**

- 크롤링의 출발점
- 서비스 목적에 따라 다르게 선정
  - 예: 국가별, 도메인별, 특정 서비스 범위

**(2) 미수집 URL 저장소**

- 아직 방문하지 않은 URL을 관리하는 저장소
- 기본적으로 FIFO 큐 형태
- 실제로는 예의, 우선순위, 신선도를 고려해 관리됨

**(3) HTML 다운로더**

- URL을 받아 웹 서버에 요청을 보내고 HTML을 수신
- 네트워크 오류, 타임아웃, 비정상 응답을 고려해야 함

**(4) 도메인 이름 변환기**

- URL의 도메인 이름을 IP 주소로 변환

**(5) 콘텐츠 파서**

- HTML 문서를 분석
- 비정상 페이지, 처리 불가능한 콘텐츠를 판별

**(6) 중복 콘텐츠 판별**

- 웹 페이지 내용을 해시로 변환
- 이미 수집된 콘텐츠와 비교하여 중복 여부 판단

**(7) 콘텐츠 저장소**

- 다운로드한 HTML 문서를 저장
- 이후 검색, 분석, 인덱싱 등에 사용

**(8) URL 추출기**

- HTML 문서에서 링크(URL)를 추출

**(9) URL 필터**

- 접근 불가하거나 의미 없는 URL 제거
  - 에러 URL
  - 특정 확장자
  - 정책상 제외 대상

**(10) 방문 여부 확인**

- 이미 방문한 URL인지 확인
- Bloom Filter 또는 해시 테이블 활용

**(11) URL 저장소**

- 이미 방문한 URL을 저장
- 동일 URL의 재수집 방지 목적

## 3. 상세 설계

### DFS vs BFS

웹은 깊이를 예측하기 어려운 그래프 구조를 가지므로  
DFS는 특정 사이트에 과도하게 빠질 위험이 있다.

따라서 웹 크롤러는 일반적으로 **BFS(너비 우선 탐색)**를 사용한다.

다만 BFS만 사용하면 다음 문제가 발생한다.

- 특정 서버로 요청이 집중됨
- URL 간 중요도 구분이 없음

### 미수집 URL 저장소 개선

**(1) 예의 (Politeness)**

- 동일 서버에 과도한 요청을 보내지 않도록 제어
- 도메인별 요청 간격 유지

**(2) 우선순위**

- 모든 페이지를 동일하게 처리하지 않음
- 중요 페이지를 먼저 수집하도록 우선순위 부여

**(3) 신선도**

- 웹 페이지는 지속적으로 변경됨
- 주기적 재수집 필요

방법:
- 변경 이력 기반 재수집

### HTML 다운로더 고려 사항

**(1) 성능**

- 병렬 다운로드
- 커넥션 재사용

**(2) 안정성**

- 타임아웃 설정
- 재시도 횟수 제한

**(3) 확장성**

- 여러 다운로드 노드로 분산 처리

**(4) 문제 있는 콘텐츠 처리**

1. **중복 콘텐츠**: 불필요한 저장 및 처리 방지  
2. **거미 덫**: 무한히 생성되는 URL 구조 회피  
3. **데이터 노이즈**: 광고, 의미 없는 페이지 제거  

## 4. 추가 고려 사항

- 서버 사이드 렌더링(동적 페이지 처리)
- 페이지 필터링 정책
- 데이터베이스 다중화 및 샤딩
- 수평적 확장 구조
- 가용성, 일관성, 안정성
- 수집 데이터 분석 및 활용

# ch 10. 알람 시스템 설계

## 1. 문제 이해 및 설계 범위 확정

- 푸시 알림, SMS 메시지, 이메일을 지원해야 한다.
- 연성 실시간 시스템이라고 가정한다.
  - 알림은 가능한 한 빨리 전달되어야 하지만
  - 시스템에 높은 부하가 걸렸을 때 약간의 지연은 허용한다.
- iOS, Android, 데스크톱을 지원해야 한다.
- 알림은 클라이언트 애플리케이션 혹은 서버 측 스케줄링으로 생성할 수 있다.
- 사용자는 알림을 받지 않도록 설정할 수 있다.
- 다음 규모를 처리할 수 있어야 한다.
  - 천만 건의 모바일 푸시 알림
  - 백만 건의 SMS 메시지
  - 5백만 건의 이메일

## 2. 개략적 설계안

- 알림 유형별 지원 방안
- 연락처 정보 수집 절차
- 알림 전송 및 수신 절차

### 알림 유형별 지원 방안

**(1) iOS 푸시 알림**

iOS에서 푸시 알림을 보내기 위해서는 다음 세 가지 컴포넌트가 필요하다.

- 알림 제공자(Provider)
  - 알림 요청(notification request)을 생성하여 APNS로 전송
- APNS (Apple Push Notification Service)
  - 애플이 제공하는 원격 푸시 알림 서비스
- iOS 단말
  - 푸시 알림을 수신하는 사용자 장치

**(2) 안드로이드 푸시 알림**

- iOS 푸시 알림과 유사한 구조
- APNS 대신 FCM(Firebase Cloud Messaging)을 사용

**(3) SMS 메시지**

- 외부 SMS 서비스 제공자와 연동하여 전송

**(4) 이메일**

- 이메일 서버 또는 외부 이메일 서비스와 연동하여 전송

### 연락처 정보 수집 절차

알림을 전송하기 위해서는 다음과 같은 정보가 필요하다.

- 모바일 단말 토큰
- 전화번호
- 이메일 주소

사용자가 앱을 설치하거나 계정을 처음 등록할 때,  
API 서버는 해당 정보를 수집하여 데이터베이스에 저장한다.

### 알림 전송 및 수신 절차

- 이벤트 또는 스케줄에 의해 알림 생성
- 사용자 설정 확인
- 알림 유형에 맞는 전송 채널 선택
- 외부 푸시 / SMS / 이메일 서비스로 전달
- 사용자 단말에서 알림 수신

### 개선된 설계안

- 데이터베이스와 캐시를 알림 시스템의 주 서버에서 분리
- 알림 서버를 증설하여 자동으로 수평적 확장이 가능하도록 구성
- 메시지 큐를 사용해 시스템 컴포넌트 간의 강한 결합 제거

## 3. 마무리

- 안정성
- 보안
  - 인증된 클라이언트만 알림을 전송할 수 있도록
  - appKey, appSecret 등의 인증 메커니즘 사용
- 이벤트 추적 및 모니터링
- 사용자 알림 설정 관리
